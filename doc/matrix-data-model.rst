矩阵数据结构与关系规范
============================================================

本文件是后续数据库与关系维护的设计依据。适用于新增或调整表、字段、外键、主明细、交付来源、工作空间引用、对象归类和导入关联。Agent应先确定变更在矩阵中的归属及引用方向，再修改对应实现，并同步验证矩阵结果。

本规范依据2026-11-15当前实现和用户在本次对话中的要求整理。新的明确业务要求可以修订矩阵；应说明归属或关系的变化并同步本文，不能为了保持旧截图而阻止已授权的业务调整，也不能从空格或隐藏箭头推定删表、删字段或删外键。

矩阵的两个维度
------------------------------------------------------------

横轴表示唯一主录的责任部门，当前对应六个业务schema：

.. list-table::
   :header-rows: 1
   :widths: auto

   * - 部门
     - schema
     - 主要归属
   * - 财务
     - finance
     - 资金、会计记录、财务核对、人员及会计基础资料。
   * - 法务
     - legal
     - 公司主体、法律及适用规则资料、合同审阅和合规事项。
   * - 生产
     - production
     - 供应商、采购、仓储、库存、生产执行及履约实物事件。
   * - 研发
     - rd
     - 产品物料、版本、单位、BOM、项目、设计和发布依据。
   * - 销售
     - sales
     - 客户、渠道、需求、合同订单及售后业务。
   * - 分析
     - analysis
     - 数据来源、模型及指标、报告、意见规划和效果复盘。

纵轴表示内容职责。它不是七个新schema，也不是七张固定业务表；审计、部门交付及历史来源均不是新增部门。

.. list-table::
   :header-rows: 1
   :widths: auto

   * - 内容
     - 内部area
     - 结构含义与边界
   * - 计划
     - plans
     - 目标、意向与规划；当前包括历史生产草稿、分析意见规划及文件计划。计划不自动成为订单、实际产出或库存增加。
   * - 工作流
     - workflow
     - 采纳、执行、整改和状态处理；生产执行主单也在这一层。新文件事项与保留的旧SQL表并存，不能因同在一格就重复维护同一事实。
   * - 活动数据
     - data
     - 实际业务事件、主明细、明确对应关系，以及分析计算、报告等已登记事实；不能由付款推定到货、成本或收入确认。
   * - 静态数据
     - archive
     - 可复用档案、版本、规则、单位、模型和指标定义。archive是现有内部键，不因界面改名重新建表。
   * - 审计
     - audit
     - 核定与核对职责，包括财务核对表及按责任部门归属的文件审计报告。文件报告按起止日期登记，不恢复旧月／季／年分类字段。
   * - 部门交付
     - delivery
     - 本部门交付记录与交付明细；通过ID引用本部门原始主录，不把交付内容复制为另一部门可独立维护的事实。
   * - 历史来源
     - history
     - 历史、技术支撑及对账明细。是否允许新增或修改由实际录入／导入规则决定，不因位于此行就统一设为只读或删除。

一个格子的键为 ``area:schema``，例如 ``data:rd``。格子内可以有多张主录或明细表、多条文件工作空间记录；它只是归属汇总，不是新的数据库实体。

归属与存储依据
------------------------------------------------------------

- 一个事实只在发生部门维护一处权威主录；其他部门通过ID引用。表、表中一行记录、矩阵格子是三个不同层级，不能互相替代。
- SQL对象以 ``schema.表名`` 唯一识别，列归属由实际schema确定，行归属由 ``app/workspace_rules.py`` 的 ``presentation()`` 给出。``app/data.py`` 的 ``catalog()`` 读取当前库结构并附加归类；前端不另外维护一张假想的关系表。
- ``area``、``retired`` 和 ``standalone`` 是不同属性。旧流程表可能仍归工作流，技术明细可能没有独立入口；不能把所有retired对象改归历史行，也不能因为不能独立录入就从结构矩阵排除。
- SQL格子的计数按目录中的不同 ``schema.表名`` 计算，包括保留的历史及支撑表，不是这些表的业务行数。没有业务行的真实表仍占一个结构对象；不能把空表从矩阵删掉。
- 计划、工作流及审计报告目前另有文件存储，分别按 ``plan → plans``、``workflow → workflow``、``report → audit`` 归行，按记录明确的department及现有别名归列。未指定或无法识别的部门不计入六列，不自动猜归属。
- 同一格在SQL对象数上再加已明确归属的文件记录数，形成页面的“已知主录／记录”数量。这是混合目录计数，不是去重后的业务事实总量；不要用它计算业务发生笔数。
- 文件目录由所选数据库来源的 ``workspace_directory`` 和 ``ERP.workspace_root()`` 解析，默认位置才是 ``var/workspace/``；正式、演示和自定义来源必须隔离，不能假设都在项目目录或同一个集群。数据库dump不包含这些文件。
- 来源中的原件、候选映射、真实主录、发布交付与计算结果保持可追溯且可区分。金额／数量精度、NULL与真实0、币种、单位、主体、日期及三个业务标识继续遵守现有全局规则。

箭头与底层关系
------------------------------------------------------------

箭头统一表示“引用方 → 被引用方”，不是业务时间顺序、物流流向、金额流向或处理成功状态。例如工作流事项通过plan_id引用计划时，箭头是工作流格指向计划格，并不表示业务先执行再规划。

关系分三类读取：

.. list-table::
   :header-rows: 1
   :widths: auto

   * - 来源
     - 当前形成箭头的依据
     - 不能据此认定的事项
   * - SQL外键
     - ``/api/meta`` 的references来自当前库 ``pg_constraint``，定位到来源表／列和目标表／列，标记为FK。
     - 有约束不等于已有业务行、关联列已填写或业务已核定。
   * - 文件plan_id
     - 当前来源中明确的计划编号引用；保存服务核对该计划存在于当前来源。
     - 不把文件引用称为PostgreSQL外键，不跨来源拼接计划。
   * - 文件links
     - 每行 ``schema.表名:记录ID``；矩阵在目标表已知且ID文本非空时表示该声明。
     - 绘图没有逐个查询目标ID是否存在，不能把画出的箭头当作有效性校验。保存或导入关联仍需按实际接口核对对象、ID及来源。

SQL目录与文件记录在绘图前合并，多个明细关系如果落在相同的“来源格 → 目标格”，就合为一个有向箭头，具体表／字段依据仍在证据列表中。反方向另算一个方向；选中格展示直接相连的出向和入向关系，不自动追加传递依赖。页面“引用方向”数量是这种格子间方向数，不是外键条数、记录数或关系基数。

主明细的1:N、多对多的M:N、唯一性、可空性、删除行为和发布保护不能从一个聚合箭头反推。它们仍由逐表规范、真实DDL、保存逻辑及业务核对确定；M:N需要有明确粒度和自身ID的对应明细，不能把多个ID拼进普通SQL字段来替代关系。

当前已核对的关系示例：

.. list-table::
   :header-rows: 1
   :widths: auto

   * - 来源格 → 目标格
     - 实际引用
     - 含义
   * - workflow:production → data:rd
     - ``production.生产工单表.发布批次ID → rd.发布批次表.发布批次ID``
     - 生产执行采用明确的研发发布依据，不复制一份BOM另行维护。
   * - data:rd → archive:rd
     - ``rd.BOM登记表.产品版本ID → rd.产品版本表.产品版本ID``
     - 活动记录引用产品版本；同一部门内跨内容行也有关系。
   * - data:sales → archive:rd
     - ``sales.销售订单行表.产品版本ID → rd.产品版本表.产品版本ID``
     - 销售订单行引用研发持有的版本身份，不通过相似名称猜版本。
   * - data:analysis → delivery:finance
     - ``analysis.数据集输入来源表.finance交付ID → finance.交付记录表.交付ID``
     - 分析通过财务交付保持输入来源；其他部门交付有各自明确的来源列。
   * - delivery:rd → data:rd
     - ``rd.交付明细表.BOM登记表引用 → rd.BOM登记表.BOM登记ID``
     - 交付明细引用原主录；交付不改变原主录的所有权，也不自动冻结其可变字段。
   * - data:sales → data:sales（界面隐藏）
     - ``sales.销售订单行表.订单ID → sales.销售订单登记表.订单ID``
     - 两张表位于同一格，底层1:N关系与外键仍然保留。

界面隐藏规则与数据边界
------------------------------------------------------------

- 格子的SQL对象数与已归属文件记录数都为0时，只留空白占位以保持六列七行对齐，不显示文字或边框、不可选中。它表达当前没有已知对象或记录，不表达该部门没有职责，也不是自动新建表的清单。
- 来源格等于目标格时，不绘制箭头、不计入引用方向、不列入该图的关系证据。这包括同表自引用，也包括两张不同表位于同一格的关系；不是只判断表名相同。
- 上述隐藏只发生在矩阵展示聚合层，不删除表、行、外键、关联字段、原始来源或历史引用。需要检查完整关系时读取references、DDL和原始记录，不能只看屏幕。
- 有历史FK可见，不代表允许新建记录继续引用退役字段；现有写入／导入规则仍生效。界面入口合并或名称变化，也不自动授权物理合表。
- 视觉保留选中格蓝底白字、关联格蓝框、其他已知格文字变淡；半透明曲线按位置选择四边起终点并分散落点，文字位于上层，悬停／聚焦关联格强调对应曲线。箭头方向始终由真实引用决定，不由曲线弯向或屏幕位置决定。
- 矩阵使用当前来源的结构及文件引用；当前文件读取不套用页面起止日期，因此不是选定期间的交易图。空白格、N/A和无箭头均不能据以认定业务已经完整登记或核定。

后续Agent修改数据库与关系的方法
------------------------------------------------------------

1. 先读取本文、全局规则、相关逐表定义和当前实现。解析所选mode／db的实际数据库与文件工作空间目录，再通过只读元数据核对对象、字段、主键、外键和归类；历史截图、表数或报告只作线索。
2. 为本次变更说明最小关系信息：事实及其唯一维护部门、来源格／对象／字段、目标格／对象／主键、1:1或1:N或M:N、可空性、保存位置、历史数据／引用和受影响的交付或导入。已有授权范围内直接推进，不为填写这份说明重复申请批准；确实缺少的业务含义保留待定。
3. 新主录先确定唯一归属和行粒度；新增引用先确定已有目标及真实ID。名称相近不自动合表，同一字段不能在多个部门各维护一份权威事实。业务流程需要跨部门引用时如实保留，不为了减少箭头复制目标数据或改反方向。
4. SQL关系在真实结构中维护外键、主明细／对应表和适用约束；文件关系在对应工作空间及服务校验中维护。不能只在前端画线、手填方向数或改分类来掩盖结构不一致；不能把同格关系的显示过滤移到数据库约束删除逻辑。
5. 按影响范围同步：业务意义在全局／逐表规范；基础SQL通过构建器生成db与清单，已有库通过已实现的受控迁移升级；归类改 ``workspace_rules.py``；元数据改 ``data.py``；文件关系改 ``workspace.py`` 及工作空间界面；关联选择／来源提示、录入、导入模板和相关核对同步。只更新实际受影响的部分。
6. 修改正式结构前按所选来源备份数据库；涉及文件记录同时备份对应工作空间。样例写入演示或隔离库，保留ID、原始来源、版本与审计；不靠重建正式库、清空表或改业务事实来符合矩阵。
7. 在相同来源比较变更前后：对象的格子归属、实际外键及其入向／出向、主明细基数和可空性、文件引用目标、既有记录及追溯。关系变更需核对矩阵聚合证据；界面变更再验证曲线方向、四边落点、空格隐藏、同格箭头隐藏、悬停、三态切换、主题和窄屏。没有业务行的表仍应显示结构对象。
8. 交付说明矩阵哪几个格子及关系发生变化、实际执行的静态／数据库／浏览器验证、备份和未核定项。若用户要求改变部门或内容模型，同步本文、AGENTS.md及相关Skills；不要把旧格子数量变成永久业务限制。

量化计算（2026-11-15更新）
------------------------------------------------------------

左栏“计划”入口改为“量化计算”，不选择部门、不按业务日期筛选。列表仅有ID与备注，行内“计算台”保存LaTeX公式、参数及派生结果；可选“结果写入备注并保存”。不再使用顶栏浮动计算器。旧计划URL转入量化计算，旧计划及生产意向原件、plan_id引用与历史查询保留，不自动转成计算记录。

量化计算是六部门矩阵之外的独立文件空间，路径为所选来源workspace_directory下calculations/live.json或demo.json；无部门、责任人、计划状态或期限字段，不建立SQL业务表或外键。ID用CAL短号，长号为WS-CAL命名空间，版本、幂等、历史与原子写为技术元数据。每个条目1:1持有计算台；计算结果只派生于该条目显式公式与十进制参数，不引用或回写库存、订单、财务和其他业务数据。矩阵中的plans行改称“历史计划”，继续表示已有对象及原plan_id/links，不把无部门计算记录分配到任何部门格。

浏览器本地即时预览，服务端保存时用有理数重新计算，结果最多20位小数并标注近似；未知参数留空、错误不填零。新存储不改写既有工作空间文件。备份整个workspace目录包含该目录，数据库dump不包含这些文件。接口GET /api/calculations、POST /api/calculations/save沿用所选mode/db、本机/同源和令牌验证；更新携带version，重试保留request_id。Agent使用easyerp-calculations Skill及其脚本，与界面共用保存服务。
